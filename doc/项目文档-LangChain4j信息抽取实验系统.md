# 基于 LangChain4j 的中英双语招聘信息抽取实验系统

## 1. 项目概述

### 1.1 项目名称
基于 LangChain4j 的中英双语招聘信息抽取实验系统

### 1.2 项目背景
信息抽取是自然语言处理中的重要任务，其目标是从非结构化文本中抽取出结构化信息。传统的信息抽取方法通常依赖规则、词典或统计学习模型，在特定场景下具有较好的可解释性和较低的实现成本；而大语言模型具备更强的语义理解与泛化能力，能够在复杂表达、多样句式和中英混合文本中提升抽取效果。

LangChain4j 是面向 Java 生态的大模型应用开发框架，适合将大语言模型能力与本地语料管理、规则抽取、结果评估等模块结合起来。因此，本项目计划基于 LangChain4j 设计并实现一个面向特定领域语料的信息抽取实验系统，通过“规则抽取 + 大模型抽取”的组合方式，对比不同方法在真实文本中的表现。

### 1.3 项目目标
构建一个可运行的信息抽取实验系统，满足课程作业要求，并具备一定扩展性。系统目标如下：

1. 选择一个感兴趣的特定领域，建立不少于 100 篇文档的本地语料库。
2. 围绕该领域设计不少于 5 个特定信息点，并完成抽取。
3. 至少实现基于正则表达式匹配的特定信息点抽取。
4. 使用 LangChain4j 接入大语言模型，实现结构化信息抽取。
5. 对抽取结果进行展示，并尽量开展人工准确率评估。
6. 为后续扩展到检索增强、向量检索、更多 NLP 基础模块打下基础。

## 2. 选题与语料设计

### 2.1 选题方向
本项目选取“中英双语招聘信息”作为特定领域语料。

选择该领域的原因如下：

1. 招聘文本结构相对稳定，便于设计规则抽取。
2. 招聘文本中包含丰富的关键实体，适合做多字段抽取。
3. 中英文招聘信息都较常见，适合体现系统的双语适应能力。
4. 该领域具有较强现实意义，结果易于理解和展示。

### 2.2 语料来源
语料可来自以下几类来源：

1. 公开招聘网站的岗位描述页面。
2. 企业官网招聘公告。
3. 自行整理或仿写的招聘文本样本。
4. 中英文混合招聘信息数据集。

为避免采集难度过大，项目实现时可采用“公开文本整理 + 人工补充构造”的方式，确保最终本地存储文档数不少于 100 篇。建议语料规模为 120 至 200 篇。

### 2.3 本地存储形式
每篇文档单独存储为一个 `.txt` 或 `.json` 文件，统一放置在本地目录中，例如：

```text
data/corpus/
  zh_001.txt
  zh_002.txt
  ...
  en_001.txt
  en_002.txt
```

也可额外维护一个元数据文件：

```json
{
  "id": "zh_001",
  "language": "zh",
  "source": "company_site",
  "title": "Java开发工程师",
  "text": "岗位职责：......"
}
```

## 3. 抽取目标设计

### 3.1 特定信息点
本项目针对招聘信息设计以下 7 个信息点，满足作业“特定信息点不少于 5 个”的要求：

1. `job_title`：岗位名称
2. `company_name`：公司名称
3. `work_location`：工作地点
4. `salary`：薪资范围
5. `education`：学历要求
6. `experience`：工作经验要求
7. `skills`：技能要求

### 3.2 信息点说明

#### 1. 岗位名称
通常出现在标题或正文开头，如“招聘 Java 开发工程师”“Senior Backend Engineer”。

#### 2. 公司名称
常见于文本首部、落款、招聘主体介绍部分。

#### 3. 工作地点
可表现为“工作地点：北京”“Base: Shanghai”“Location: Remote”等。

#### 4. 薪资范围
中文中可能表现为“15k-25k/月”“年薪 30 万起”；英文中可能为“20k-30k CNY/month”“USD 40k-60k annually”。

#### 5. 学历要求
常见表达如“本科及以上”“硕士优先”“Bachelor's degree required”。

#### 6. 工作经验
常见表达如“3 年以上经验”“1-3 years experience”“experienced candidates preferred”。

#### 7. 技能要求
如“熟悉 Java、SpringBoot、MySQL”“proficient in Python, NLP, TensorFlow”。

## 4. 系统总体设计

### 4.1 总体思路
系统采用“本地语料管理 + 预处理 + 规则抽取 + 大模型抽取 + 结果展示 + 人工评估”的流程。

整体流程如下：

```text
本地语料库
   ↓
文本预处理
   ↓
规则抽取（正则表达式）
   ↓
大模型抽取（LangChain4j）
   ↓
结果融合与存储
   ↓
结果展示与人工评估
```

### 4.2 模块划分
系统可划分为以下模块：

1. 语料管理模块
2. 文本预处理模块
3. 规则抽取模块
4. 大模型抽取模块
5. 结果存储模块
6. 结果展示模块
7. 评估模块

## 6. 功能模块详细设计

### 6.1 语料管理模块

#### 功能
1. 扫描本地语料目录。
2. 读取中英文文本。
3. 对每篇文档分配唯一编号。
4. 提供批量处理入口。

#### 输入
本地招聘文本文件。

#### 输出
统一格式的 `DocumentRecord` 对象列表。

#### 建议数据结构
```java
public class DocumentRecord {
    private String id;
    private String language;
    private String title;
    private String text;
}
```

### 6.2 文本预处理模块

#### 功能
1. 去除多余空格、HTML 标签、特殊符号。
2. 进行中英文分句。
3. 根据需要进行分词、命名实体识别等基础处理。

#### 可选基础 NLP 工具
1. HanLP
2. Jieba
3. Stanford CoreNLP
4. OpenNLP

说明：作业要求允许调用开源的中英文 NLP 基本模块，因此可以在预处理阶段引入 HanLP 或 CoreNLP 作为辅助工具，但本项目核心仍是信息抽取实验流程。

### 6.3 规则抽取模块

#### 功能
使用正则表达式完成至少部分字段的抽取，满足课程“至少实现正则表达式匹配算法”的要求。

#### 适合使用正则抽取的字段
1. `salary`
2. `education`
3. `experience`
4. `work_location`

#### 正则示例

薪资抽取示例：

```regex
(\d{1,2}[kK]-\d{1,2}[kK])|(\d{1,2}[-~]\d{1,2}万/年)|(\$\d{2,3}k-\$\d{2,3}k)
```

学历抽取示例：

```regex
(大专|本科|硕士|博士|本科及以上|硕士及以上|Bachelor'?s degree|Master'?s degree|PhD)
```

经验抽取示例：

```regex
(\d+[-~]?\d*年经验)|(\d+\+?\s*years? of experience)
```

#### 优点
1. 实现简单。
2. 可解释性强。
3. 对格式固定字段效果较好。

#### 局限
1. 对表达多样性适应较弱。
2. 对隐式信息抽取效果不佳。

### 6.4 大模型抽取模块

#### 功能
利用 LangChain4j 调用大模型，对整篇招聘文本进行结构化信息抽取。

#### 设计方式
将抽取任务描述为一个提示词模板，要求模型直接返回结构化 JSON 或映射到 Java Bean。

#### 建议提示词
```text
请从下面的招聘文本中抽取结构化信息，返回以下字段：
job_title, company_name, work_location, salary, education, experience, skills

要求：
1. 若某字段不存在，返回 null。
2. 保持原文含义，不要编造。
3. 结果以 JSON 格式返回。
```

#### 建议输出对象
```java
public class ExtractionResult {
    private String documentId;
    private String jobTitle;
    private String companyName;
    private String workLocation;
    private String salary;
    private String education;
    private String experience;
    private List<String> skills;
    private String extractorType;
}
```

#### 预期优势
1. 能处理较灵活的文本表达。
2. 能利用上下文语义补全隐式信息。
3. 对中英文混合文本适应更强。

### 6.5 结果融合模块

#### 功能
将规则抽取结果与大模型抽取结果进行统一存储，可采用以下策略：

1. 分开保存，便于对比实验。
2. 优先采用规则结果，再用大模型补全缺失字段。
3. 对冲突字段进行标记，供人工复核。

建议保留两套结果：

1. `regex_results.json`
2. `llm_results.json`

如需进一步实验，也可生成：

3. `merged_results.json`

### 6.6 结果展示模块

#### 展示方式一：命令行
对每篇文档输出抽取结果摘要，例如：

```text
文档ID: zh_001
岗位名称: Java开发工程师
公司名称: 某科技公司
工作地点: 北京
薪资: 20k-30k/月
学历: 本科及以上
经验: 3年以上
技能: Java, Spring Boot, MySQL
```

#### 展示方式二：简单 Web 界面
可基于 Spring Boot + Thymeleaf 或前后端分离方式实现：

1. 文档列表页
2. 原文查看页
3. 抽取结果展示页
4. 规则结果与 LLM 结果对比页

### 6.7 评估模块

#### 功能
对抽取结果进行人工标注评估。

#### 评估方式
从 100+ 篇文档中随机抽取 20 至 30 篇，人工标注标准答案，形成 `golden_labels.json`，然后分别计算规则抽取和大模型抽取的效果。

#### 指标
1. Precision（准确率）
2. Recall（召回率）
3. F1-score

若实现时间有限，也可以至少统计“字段级准确率”。

#### 示例
若 25 篇文档共评估 7 个字段，则总字段数为 175。假设其中正确抽取 145 个，则字段级准确率为：

```text
Accuracy = 145 / 175 = 82.86%
```

## 8. 实验流程设计

### 8.1 实验步骤

1. 收集并整理招聘领域中英文语料，不少于 100 篇。
2. 将语料存储到本地目录。
3. 编写预处理模块，完成文本清洗。
4. 编写正则抽取器，实现基础字段抽取。
5. 使用 LangChain4j 接入大模型，实现结构化抽取。
6. 保存两类抽取结果。
7. 进行人工抽样标注，构建评估集。
8. 比较规则方法与大模型方法的抽取效果。
9. 总结实验结果与改进方向。

### 8.2 对比实验设计

可设置以下三组实验：

1. 仅使用正则表达式抽取。
2. 仅使用大模型抽取。
3. 规则抽取 + 大模型补全融合。

通过比较三种方案的字段级准确率，分析不同方法的优缺点。

## 9. 预期结果与分析

### 9.1 预期结果

1. 正则方法在薪资、学历、经验等格式化字段上效果较好。
2. 大模型方法在岗位名称、技能要求、公司名称等复杂语义字段上效果更优。
3. 融合方案整体效果最好，兼顾稳定性与语义理解能力。

### 9.2 可能问题

1. 招聘文本格式差异较大，影响规则泛化。
2. 大模型可能出现幻觉，补出原文没有的信息。
3. 中英混合文本中某些字段边界不清晰。
4. 技能字段可能存在枚举不全或拆分不准的问题。

### 9.3 优化方向

1. 引入分词、NER、句法分析增强候选字段定位。
2. 引入 few-shot prompt 提升大模型输出稳定性。
3. 对技能词建立词典，结合规则和语义抽取。
4. 对抽取结果做后处理和标准化，例如统一薪资单位、地点名称。

## 10. 算法优化设计

在完成基础版本“正则抽取 + LangChain4j 大模型抽取”之后，本项目可以从规则优化、提示词优化、融合优化和基础 NLP 增强四个方面开展算法改进，并通过对比实验验证优化效果。

### 10.1 规则抽取优化

基础正则抽取虽然实现简单，但在跨语言、多样表达和复杂上下文中存在明显局限，因此可从以下几个方向优化：

1. 为不同字段分别设计中英文规则模板，例如薪资、学历、经验、地点维护独立模式。
2. 增加字段标准化处理，将“15k-25k/月”“20万/年”“USD 40k-60k annually”等形式统一为标准表示。
3. 增加上下文规则，不仅匹配字段值本身，还结合“岗位职责”“任职要求”“工作地点”等标题区域进行辅助判断。
4. 对技能字段引入专业词典匹配与规则补全，提高技能枚举抽取的稳定性。

### 10.2 大模型提示词优化

LangChain4j 接入大模型后，可以通过提示词工程提升结构化抽取稳定性。具体优化思路如下：

1. 比较 zero-shot 与 few-shot 提示方式对抽取结果的影响。
2. 使用强约束 JSON 输出模板，减少大模型输出格式不稳定的问题。
3. 将“一次性抽取全部字段”优化为“先定位候选句，再按字段抽取”的两阶段流程。
4. 对中英文文本分别设计提示模板，以减少语言混合带来的歧义。

### 10.3 规则与大模型融合优化

项目可进一步设计规则方法与大模型方法的协同机制，而不是简单二选一。建议尝试以下融合策略：

1. 规则优先：规则能稳定抽取的字段直接采用规则结果，缺失部分由大模型补全。
2. 大模型优先：由大模型完成初步抽取，再由规则模块对薪资、学历、经验等关键字段做校验。
3. 字段级融合：格式稳定字段采用规则优先，语义复杂字段采用大模型优先。
4. 冲突检测：当规则结果与大模型结果不一致时，对结果进行标记，交由人工复核。

该融合设计适合形成对比实验，比较“仅规则”“仅大模型”“融合方法”三种方案的效果差异。

### 10.4 基础 NLP 模块增强

为了使系统更接近完整的信息抽取实验平台，可以引入开源 NLP 基础模块作为辅助：

1. 分句：将长文本切分为短句，提高候选信息定位能力。
2. 分词：辅助中文技能词识别与规则匹配。
3. 命名实体识别：辅助公司名、地点名、岗位名等实体字段抽取。
4. 关键词提取：先筛选可能包含目标字段的句子，再进行细粒度抽取。

### 10.5 评估驱动优化

算法优化不应仅停留在方法设计层面，还应建立误差分析机制。可开展以下评估：

1. 统计字段级准确率、召回率与 F1 值。
2. 分字段评估不同算法表现，例如薪资字段、技能字段分别统计。
3. 分中英文场景评估模型稳定性。
4. 对错误案例进行分类，如漏抽、误抽、边界错误、模型幻觉、规则误匹配等。

通过上述分析，可以进一步指导规则模板、提示词模板和融合策略的改进。

## 11. 多媒体信息抽取扩展设计

除纯文本招聘语料外，本项目还可以扩展到招聘海报、招聘简章 PDF、网页截图等多媒体材料，从而形成多源信息抽取系统。

### 11.1 扩展动机

实际招聘信息并不总以纯文本形式出现，很多岗位信息来自：

1. 图片招聘海报
2. 企业发布的 PDF 招聘简章
3. 社交媒体推文截图
4. 图文混排的长图公告

因此，可将多媒体信息抽取作为本项目的扩展方向，以响应课程对多媒体信息抽取的鼓励要求。

### 11.2 基本处理流程

多媒体信息抽取的总体思路不是重新设计一套全新抽取器，而是先将图片或 PDF 转换为文本，再复用原有文本抽取流程。处理链路如下：

```text
图片 / PDF / 网页截图
   ↓
OCR 文字识别
   ↓
文本清洗与版面重组
   ↓
规则抽取 / 大模型抽取 / 融合抽取
   ↓
结构化结果输出
```

### 11.3 可引入的工具模块

1. OCR 模块：如 PaddleOCR、Tesseract OCR，用于从图片和扫描版 PDF 中提取文字。
2. 版面重组模块：按照文本块坐标进行排序与合并，恢复较合理的阅读顺序。
3. OCR 纠错模块：对邮箱、电话、薪资等易错字段做规则校验与修正。
4. 统一抽取模块：对 OCR 输出文本复用现有正则抽取器和大模型抽取器。

### 11.4 多媒体扩展实验设计

为控制实现成本，建议将多媒体部分设计为扩展实验，而不是替代主实验。可采用如下方案：

1. 主实验：使用 100 篇以上纯文本招聘语料完成系统主体实验。
2. 扩展实验：补充 10 至 20 个招聘海报或 PDF 案例。
3. 对比分析：比较原始文本抽取、OCR 后抽取以及不同图片质量下的抽取效果差异。

### 11.5 多媒体方向的优化点

1. OCR 结果纠错：修正常见字符识别错误。
2. 版面感知抽取：利用标题区域、底部区域、表格区域等位置信息辅助字段判断。
3. OCR + 大模型联合抽取：先 OCR，再由 LLM 做结构化抽取，最后由规则做字段校验。
4. 噪声鲁棒性评估：分析模糊图片、倾斜文本、长图拼接等场景下的抽取表现。

## 12. 基于竞赛算法工具调用的多工具协同抽取方案

在基础系统之上，本项目还可以进一步吸收信息抽取竞赛与研究中的代表性算法，将其封装为独立工具模块，并利用 LangChain4j 让大模型根据任务特点选择最合适的抽取工具。

### 12.1 设计思想

传统方案通常是“固定算法处理全部字段”，而本项目可升级为“多工具协同 + 大模型路由”架构。其核心思想是：

1. 将不同抽取算法封装为独立工具。
2. 为每种工具定义适用场景、优势与局限。
3. 由大模型分析当前文本特点和目标字段类型。
4. 自动选择最合适的工具或工具组合执行抽取。
5. 对多个工具输出结果进行融合、校验和补全。

这种设计既利用了大模型的语义判断能力，也保留了传统信息抽取算法在特定任务上的稳定性和专业性。

### 12.2 可封装的抽取工具类型

#### 1. 规则抽取工具

适合格式稳定字段，如：

1. 薪资
2. 学历
3. 工作经验
4. 联系方式

该工具具有精度高、解释性强、执行速度快的优点，是课程要求中的基础算法模块。

#### 2. 通用信息抽取工具

可参考统一信息抽取方向的算法与框架，例如 UIE 类方法，用于抽取：

1. 岗位名称
2. 公司名称
3. 工作地点
4. 技能要求

这类方法的特点是能够统一处理实体、关系甚至事件抽取任务，适合复杂文本场景。

#### 3. 命名实体识别工具

可引入面向实体边界识别的算法，用于先定位候选实体，再将结果交给后续抽取器使用。其适用字段包括：

1. 公司名
2. 地点名
3. 岗位名
4. 技能词

#### 4. 关系抽取工具

如果系统后续希望输出更明确的结构关系，如“岗位-要求-技能”“岗位-地点-城市”，则可引入联合实体关系抽取工具。

#### 5. 文档级抽取工具

当字段信息分散在多个句子甚至多个段落中时，可引入文档级关系抽取思路，提升跨句整合能力。

#### 6. OCR 抽取工具

在多媒体扩展场景下，OCR 工具可作为前置工具，将图片或 PDF 转为文本，再输入后续抽取流程。

### 12.3 大模型工具选择机制

为了让大模型合理地选择工具，而不是完全自由发挥，建议采用“受约束的路由决策”模式。具体做法如下：

1. 为每个工具维护工具说明，包括输入、输出、适用场景、优势和局限。
2. 将目标任务描述和工具说明一并输入大模型。
3. 要求大模型输出工具选择结果，而不是直接输出最终抽取答案。
4. 根据选择结果调用对应工具，并返回结构化抽取结果。

示例输出格式如下：

```json
{
  "task_type": "mixed_field_extraction",
  "recommended_tools": [
    "RegexExtractor",
    "UIEExtractor"
  ],
  "reason": "salary and education are pattern-stable; skills and company_name require semantic extraction"
}
```

### 12.4 推荐的最小可行工具组合

从课程作业的可实现性出发，不建议一开始引入过多复杂模型。推荐的最小可行组合为：

1. `RegexExtractor`
2. `UIEExtractor`
3. `NERExtractor`
4. `OCRExtractor`（若开展多媒体扩展实验）

这一组合已经能够支撑一个较完整的“多工具协同信息抽取系统”，并便于后续做对比实验和结果分析。

### 12.5 实验设计建议

可设置如下实验组进行比较：

1. 仅使用规则抽取。
2. 仅使用通用信息抽取模型。
3. 大模型路由选择单一工具。
4. 大模型路由选择多工具协同抽取。
5. 多工具融合后结果输出。

通过比较这些实验组的字段级准确率、召回率和 F1 值，可以验证“多工具路由协同”是否优于单一抽取器。

### 12.6 作为课程项目创新点的表述

本方案可以作为项目创新点之一，表述为：

“本项目借鉴信息抽取竞赛与前沿研究中的代表性算法，将规则抽取、通用信息抽取、命名实体识别和 OCR 等能力封装为独立工具，并利用 LangChain4j 接入的大模型根据文本特点自动选择合适工具完成抽取，从而构建了一个多工具协同的信息抽取实验系统。”

## 16. 总结

本项目围绕“基于 LangChain4j 的信息抽取实验系统”展开，选择中英双语招聘信息作为特定领域语料，设计了岗位名称、公司名称、工作地点、薪资、学历、经验、技能要求等多个信息点，并采用“正则表达式抽取 + 大模型抽取”的方案实现结构化信息获取。该系统既满足课程对本地语料规模、信息点数量、正则算法实现、结果展示与人工评价的要求，也具备继续扩展到检索增强、算法优化与多模态抽取的基础。

在进一步完善时，项目还可以从规则模板细化、提示词优化、规则与大模型融合、多媒体信息抽取、竞赛算法工具调用等方面持续增强。若后续正式编码实现该系统，建议优先完成命令行版本，确保抽取、存储、评估链路闭环，然后再逐步增加 Web 可视化和更复杂的 NLP 模块。
